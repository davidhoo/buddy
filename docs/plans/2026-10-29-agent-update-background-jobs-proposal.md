# Agent 列表缓存与后台更新方案

日期：2026-10-29。状态：已按评审方案完成开发；本地验证与已知基线问题见第 9 节。尚未发布。

## 1. 目标与范围

用户点击“全部更新”后可以离开 Agent 页面，更新持续执行；在任何页面都能看到状态，完成后收到一次汇总。再次进入 Agent 页直接显示已有列表，扫描和版本检查按需在后台执行。上一批更新结果独立展示为“最近一次更新”。

保留现有行内高级设置、JSON 编辑、统一超时、原生 CLI/ACP 行为和安装渠道。首期覆盖缓存、后台队列、状态展示、通知、取消与退出恢复，不重做 Agent 列表，也不加入自定义 Agent 添加入口。

## 2. 实施前确认的现状

| 位置 | 当前行为 | 影响 |
| --- | --- | --- |
| `AgentsSettings.tsx` | `localAgents` 的 staleTime 为 30 秒，每次挂载还调用 `checkAgentUpdates()` | 页面进入会触发检查，列表缓存未成为统一读取入口 |
| `agents/service.ts` 的 `list()` | 内存缓存 60 秒；过期就等待扫描结束；扫描进行中也等待 | 即使已有列表，读取也可能等待 CLI 版本、帮助和 ACP 握手 |
| `agent-inventory-cache.json` | 已写入磁盘，但目前没有恢复读取逻辑 | 重启无法先显示上次发现结果 |
| `checkUpdates()` | 版本检查名义缓存 6 小时，但检查前调用 `list()`；新扫描对象未保留 `checkedAt/latest` | 本机扫描与网络检查相互牵连，缓存可能反复失效 |
| 更新队列 | 主进程异步、串行执行；IPC Promise 等整批结束；前端 busy 仅在页面组件中 | 切页不会取消，但重新进入页面无法可靠恢复忙碌状态 |
| `update()` 初始化 | `updating=true` 后先调用 `list()`，扫描在外层 try/finally 之前 | 初始扫描抛错时可能一直处于忙碌状态 |
| 更新结果 | 单个 jobs 数组持久化，并在列表下面直接逐行输出 | 活动队列与上一批结果混在一起，没有时间和汇总 |
| 互斥/取消 | 全局运行锁；占用时跳过更新；取消只阻止后续项目 | 原理保守，但等待原因和取消语义不够清楚 |

现有主进程不会因页面卸载而取消更新。macOS 关闭窗口也不自动退出进程；真正退出 Buddy 后没有可靠续跑机制。

## 3. 页面与全局交互

### 3.1 Agent 页布局

```text
Agent                           最近扫描 16:20   [刷新 ▾] [全部更新]

正在更新 · 已处理 2/5
当前：WeCode Codex · 安装中                       [取消剩余更新]

┌ Agent 列表 ───────────────────────────────────────────┐
│ Claude   版本 [高级] [更新]     CLI   模型    任务启用  │
│ Codex    版本 [高级] [验证中]   ACP   模型    任务启用  │
└──────────────────────────────────────────────────────┘

最近一次更新                              今天 16:12  [展开]
已更新 3 · 已是最新 1 · 失败 1                         [重试失败项]
```

- “正在更新”只在存在活动批次时显示。计数使用“已处理 N/M”，不把项目数伪装成下载百分比。
- 单项显示“等待中 / 检查中 / 安装中 / 验证中”等真实阶段；没有可靠进度时使用活动指示。
- “最近一次更新”放在列表下方的独立卡片。默认只显示完成时间、汇总和重试入口；明细默认收起。
- 明细包含 Agent/更新目标、更新前后版本、结果、耗时及脱敏错误；详细诊断再按需展开。
- 从未更新时不显示历史卡片；当前批次运行时仍保留上一批记录，整批结束后再替换。
- 原生渠道“检查并更新”执行后版本未变且验证通过，显示“已是最新”；未知 latest 不显示“发现新版本”。WeCode 本体与内层 CLI 的版本和动作继续分开。

### 3.2 跨页面入口

- 顶部栏放一个紧凑入口：`Agent 更新 2/5`，点击打开 Agent 页并定位活动区块。
- 在任务页、设置其他页和侧边栏折叠时都可见，适配窗口宽度；不覆盖任务自身状态。
- 整批结束时，前台显示一次非阻塞汇总；应用不在前台时，按现有系统通知开关发送一次 macOS 通知。
- 部分失败显示“3 项完成，1 项失败”，点击进入最近一次更新。按 batchId 去重，切页和重新订阅不会重复通知。
- 运行期间“全部更新”改为“更新中 N/M”并禁用；每行状态和可操作性从主进程快照推导。

## 4. 缓存策略：读取不触发扫描

### 4.1 三类数据分开

| 数据 | 建议策略 | 失效与刷新 |
| --- | --- | --- |
| 本机安装及能力快照 | 主进程内存 + 磁盘快照；启动时读取，页面直接使用 | 启动时缓存超过 10 分钟可后台扫描一次；手动重新扫描；安装/命令/参数/env 改动后只重扫受影响项 |
| 最新版本检查 | 独立按安装渠道、包身份/前缀缓存，默认 6 小时 | 应用启动按需后台检查；用户手动“检查更新”；更新对应安装后失效。普通扫描不清掉同一安装的检查结果 |
| 活动更新和上次结果 | 主进程权威快照 + 原子持久化 | 状态迁移后推送；页面只读取/订阅，不负责启动或延续任务 |

10 分钟和 6 小时为内部默认值，首期不增加用户设置项。进入页面本身不重置缓存、不发起扫描；时间过期也不使已有列表消失。

### 4.2 读取与刷新规则

1. 进入 Agent 页、打开新建任务弹窗都使用同一份全局快照；移除组件挂载时直接扫描/检查更新的 effect。
2. React Query 保留全局缓存，关闭该快照查询的自动 mount/focus 扫描；主进程推送新快照后更新查询缓存。
3. 后台刷新时继续显示旧列表与原有控件，工具栏显示“正在刷新”；不能整页闪空、重置展开状态或清空未保存表单。
4. 无任何缓存的首次启动才显示首次发现状态。扫描失败保留旧列表，显示失败原因及上次成功扫描时间；不能覆盖为空列表。
5. “刷新”主动作重新扫描并检查更新，菜单可分别执行两种只读操作；同类并发请求合并为一次执行。
6. 协议、模型、任务启用切换直接更新快照，不做全量扫描。启动目标变化只重扫该项；共享包装工具更新后刷新其关联项。
7. 磁盘缓存用 schemaVersion 校验，原子写入；仅缓存可恢复元数据，不复制密钥或完整 launcher env。读取时与当前配置合并，配置身份变化的能力结果标为待验证。
8. “上次验证通过”不是本次启动保证；实际执行/升级前重新确认目标身份和必要条件。缓存路径不会直接成为任意执行授权。
9. 主进程 revision 防止慢扫描覆盖较新的用户配置；前端表单只在有效配置变化时同步，不因版本检查结果刷新而重置。

## 5. 主进程更新任务

### 5.1 启动与数据模型

- 启动接口接受 Agent IDs 和 requestId，先保存一个 queued 批次，然后立即返回 batchId/快照；不会等待完整更新。
- 后台统一执行准备、扫描、检查、安装、验证；所有分支都受顶层 try/finally 管理，确保异常释放运行标记和租约。
- 一个主进程只有一个活动批次。重复 requestId 返回同一批次；有活动批次时再次请求返回 existingBatchId，引导查看当前进度，不仅抛技术错误。
- 主进程是唯一状态来源。单项按钮和全部更新共用执行器。

建议持久结构：

```ts
type AgentUpdateSnapshot = {
  schemaVersion: 2
  revision: number
  activeBatch?: AgentUpdateBatch
  lastCompletedBatch?: AgentUpdateBatch
}
// Batch: id、requestId、创建/开始/结束时间、状态、cancelRequested、条目和汇总
// Item: 稳定安装身份、更新目标、渠道、状态、版本前后、阶段时间、结构化结果/错误
```

批次状态：queued / preparing / waiting / running / cancelling / completed / interrupted。
单项终态区分 updated / up_to_date / failed / cancelled / interrupted / skipped。批次 completed 表示处理结束，是否全部成功由汇总表达。

开始前固定本批次目标身份；执行前再验证是否仍匹配。安装位置或包装子命令变化时重新准备或明确终止该项，不能悄悄更新另一份安装。共享安装去重沿用实际可执行文件、渠道与子命令目标；WeCode 本体升级后的内层检查按原生配置行为复核。

### 5.2 状态同步

- 增加 `buddy:getAgentUpdateState`、`buddy:startAgentUpdates`、`buddy:cancelAgentUpdates`；状态推送使用独立 `buddy:agent-update` 事件，不伪装成任务事件。
- 进程内状态更新与原子持久化串行化；写入完成后再发送新 revision。持久化失败时不启动下一项，保留可诊断的失败状态。
- App 根部常驻订阅；先订阅再获取快照，按 revision 接纳更新，避免订阅间隙与旧响应覆盖。
- 事件丢失/窗口重新打开时按快照恢复；活动期 2 秒低频补偿查询可作为兜底，结束后停止持续轮询。
- 记录读取本身无副作用；重启恢复处理在主进程初始化时只做一次。

### 5.3 与任务、扫描的协调

- 首期保留全局更新互斥，避免同时替换运行中的 Agent。已有运行自然结束；若有占用，明确显示“等待当前 Agent 运行结束”。
- 更新申请拥有排队优先权，后来的新运行不能无限插队；等待可取消，不计为任务失败，也不消耗失败重试次数。
- 新任务或后续运行轮次需要等待时，显示“等待 Agent 更新”；不能看似已经执行但实际尚未启动 CLI。
- 读取缓存与更新状态不获取执行租约，不会被更新阻塞；需要启动 CLI 的发现、模型查询按队列协调。
- 更新执行器内部验证不再次申请自己的读锁，避免自锁；取消、异常、窗口重建均验证租约最终释放。
- 安装级并发互斥留到后续；本期清楚提示全局互斥范围，不承诺不同 Agent 同时更新/运行。

### 5.4 取消、退出和崩溃

- 按钮名为“取消剩余更新”：取消未开始项；正在执行的包管理器/原生更新完成并验证后停止，不立即杀安装进程。
- 切页面、最小化、macOS 关闭窗口都继续更新。
- 用户真正退出时：有正在安装/验证的项，提供“继续后台更新”（默认）和“完成当前项后退出”；后者取消后续项，当前项验证完成再退出。
- 若尚未开始安装，可直接取消待执行队列并退出。Buddy 自身更新导致重启也需遵循同一退出协调，不能绕过安装保护。
- 强制退出/崩溃后的活动批次标为 interrupted，持久化后展示“更新被中断”。不自动重放安装命令。
- 重试前先复核是否有原更新进程仍存活（验证 PID 与进程身份，不能只凭 PID），以及安装版本/可运行性；确认无重叠执行后才恢复剩余项。
- 不承诺通用自动回滚，也不添加独立系统守护进程。用户退出 Buddy 后继续执行不属于首期目标。

## 6. 最近一次更新与迁移

- 活动批次与最近一次终态批次分开存储；新批次开始不能先抹掉上一批结果。
- 保留最后一批即可，首期不做完整历史中心。失败/中断/取消同样是值得保留的最近一次记录。
- “重试失败项”创建新批次，只包含符合条件的失败/中断项；不是把旧条目状态直接改回 running。
- 兼容旧 jobs 数组：终态记录迁入 lastCompletedBatch，活动态按中断恢复。旧记录没有完成时间时显示“旧记录 · 完成时间未记录”，不编造时间。
- 不把更新过程中的密钥、完整环境变量和未经处理的原始输出写入卡片、日志或系统通知。

## 8. 验收与测试

| 编号 | 场景 | 验收结果 |
| --- | --- | --- |
| AC-01 | 在 Agent 页与任务页之间切换 10 次，跨越原来的 30/60 秒阈值 | 列表立即显示；进入页面不启动新 CLI 扫描/网络版本检查 |
| AC-02 | 重启且存在有效缓存，后台扫描慢或失败 | 先显示缓存；扫描失败不清空列表；显示真实刷新状态/时间 |
| AC-03 | 修改模型/启用/协议，与修改命令/环境变量对比 | 前者无全量扫描；后者仅重扫受影响目标；无丢失未保存输入 |
| AC-04 | 全部更新后切页、关闭并重开窗口 | 后台继续；全局和页面显示同一 batchId/进度；不会再次创建队列 |
| AC-05 | 连点更新或多个窗口同时请求 | 同一请求幂等；同时最多一个活动批次；错误不变成重复升级 |
| AC-06 | 初始扫描、持久化、spawn、验证任一阶段失败 | 明确终态和原因；运行标记/租约释放；可以发起下一批 |
| AC-07 | 原生更新返回成功但版本不变；安装返回成功但入口不可运行 | 前者验证后显示已是最新；后者不能显示更新成功 |
| AC-08 | 有活动批次且已有上一批结果 | 正在更新与最近一次更新分区；上一批在新批次结束前不消失 |
| AC-09 | 部分失败后离开页面，再点击通知/重试失败项 | 通知只发一次；定位正确记录；只重试失败/中断项 |
| AC-10 | 取消剩余、正常退出、强制退出、遗留子进程 | 不抢杀安装；明确已完成/取消/中断；恢复时不重叠重放更新 |
| AC-11 | 任务与更新竞争、更新期间读取快照 | 等待原因可见、无饥饿/自锁、无误计任务失败；浏览页面不阻塞 |
| AC-12 | 旧文件、坏缓存、乱序事件、窗口重载 | 可控恢复/首次发现；旧 revision 不覆盖新状态；不重复通知 |

单测用可控执行器、临时安装树和虚拟时钟覆盖完整状态迁移；不要只断言命令数组。E2E 用可暂停的更新任务测试切页/重新进入、缓存命中、记录折叠、取消与完成提示，检查宽窄窗口和亮暗主题。

运行实际 Agent 时仅做只读发现与能力复核。真实更新验证使用专用测试安装，不升级用户工作环境。交付时分别报告代码/单测、页面、原生能力和实际升级的验证边界。


## 9. 实施与验证记录（2026-10-29）

### 已落地

- 库存采用内存和 v2 磁盘快照，读取与扫描拆分。启动按 10 分钟新鲜度后台发现，版本检查保留 6 小时缓存；页面进入、时间跨过旧的 30/60 秒阈值都不会触发扫描。保存参数/环境变量只刷新受影响目标。
- 缓存恢复与当前设置合并，保留 WeCode 子命令、Kimi 的原生 ACP 参数及环境继承；磁盘快照不复制 launcher 参数或环境中的凭据。配置变化、坏缓存、失败扫描均有恢复路径。
- `agents/updates.ts` 管理一个持久批次，立即接受请求，串行准备、安装、验证；重复请求复用当前批次。等待写租约具有优先权，内部验证不重复获取自己的读租约。
- 主进程向所有窗口推送独立的库存和更新事件，App 常驻订阅，按 revision 接收；仅活动期每 2 秒补偿读取。新建任务和设置共享库存缓存。
- 活动区块位于列表上方；“最后更新记录”独立位于下方，默认收起明细。顶部跨页面入口、真实阶段、完成汇总、失败重试、取消剩余、三种语言均已接入。
- 安装器先等待持久化 PID/启动时间/进程组身份，再执行真正命令；超时清理进程组。异常重启标记中断，不自动重放；重试前验证旧进程是否仍存活。
- 正常退出和 Buddy 自身升级共用退出保护：默认继续后台更新，或完成当前项及验证后退出。后台完成通知遵循系统通知开关，前台汇总按批次去重。
