当前基线为 Buddy v2.0.10、HEAD `f28cf80` 加工作区已有修改，包含 `agents/discovery.ts`、`model-cache.ts` 及 Agent/模型缓存相关改动。开始执行时重新检查 diff，不重置、覆盖或撤销其他任务的工作。

## 2. 范围和兼容约束

本任务交付两部分：**A：R1–R4 必修缺陷；B：D1–D5 原方案补全与验证**。先完成 A，再完成 B；只修完 A 时只能报告“review 缺陷已修复”，不能报告整份扩充方案已完成。

必须保持：

1. 已有任务的 Actor ID、launcher、模型、会话 ID、历史记录不变；恢复旧任务以任务自身保存的配置为准。
2. 用户显式保存的命令、参数、环境、协议和安装位置优先，不因为新发现其他安装就自动替换。
3. 新 Agent 未安装时不出现在可用任务列表，不自动下载安装；纯桌面应用没有可驱动入口时不成为 Actor。
4. 扫描不更新软件、不运行自动安装型 `npx -y`，不调用生成；保留已有更新队列与运行租约。
5. WeCode 三个包装入口保持各自语义；Codex 的现有 `CODEX_HOME`/SQLite 隔离规则保持有效。
6. 保留现有紧凑 Agent 列表和高级编辑，不恢复“添加自定义 Agent”入口，不引入插件市场或新网关。
7. JSON 写入使用原子替换，schema 集中在 `schemas.ts`；新增 UI 文案覆盖 zh-CN/zh-TW/en，使用现有图标资源或 lucide-react。
8. 本任务不包含发布、安装包替换或升级用户工作机上的 Agent。

## 3. A 部分：必修缺陷

### R1 [P1] 将自动发现的 ACP 选择贯通到任务与模型查询

**当前问题**

发现服务可以将首次发现的 Qwen 等产品标为 `selectedProtocol='acp'`，新建任务列表也允许选中，但 `CreateTaskModal` 的 `launcherFor()` 仍以全局 launcher 为依据，缺少已保存配置时默认 `cli`。最终任务拿到 CLI 命令并被 `UNADAPTED_NATIVE_EXECUTABLES` 拒绝。`isAcpActor()` 和 `listAcpModelsInner()` 也主要读取全局配置，存在同一断层。

**稳定复现**

1. 临时数据目录中不保存 Qwen launcher。
2. 临时 `qwen` 支持版本查询、ACP initialize 和 session/new。
3. 扫描后库存显示 ACP 可用，任务选择器可以选中。
4. 按真实新建任务界面提交，检查保存的 launcher；当前得到 CLI，执行报 `no native CLI adapter`。

**修改要求**

- 提供统一的协议和 launcher 解析逻辑，供 Agent 设置、新建任务、模型查询和配置保存复用，避免每处单独回退到 CLI。
- 对新任务：有效的显式用户配置优先；没有显式配置时使用发现结果的选中协议及对应 launcher。不得将 normalize 自动填充的默认值误当作用户选择。
- 对已有任务：继续使用任务自己的 launcher；不得用新库存协议覆盖它。
- 模型查询使用相同的有效启动上下文，支持尚未点击设置页保存的新发现 Agent。若现有模型查询 API 不足以表达任务上下文，应补齐参数，不用全局配置猜测旧任务的运行方式。
- 保存“启用/禁用”或模型默认值时，不应因 `configureInner()` 的 CLI 回退把自动选择的 ACP 改写为 CLI。
- 不通过扫描时批量重写全局设置来绕过问题；不删除“未适配 CLI 不得落入 contract”的保护。

**验收**

- 新装 Qwen/Copilot/Goose/Droid 无历史设置，扫描后直接新建任务，持久化的协议为 ACP，command/argv 与有效候选一致。
- 不需要先进入 Agent 设置手动切换或重新保存协议。
- 新建任务模型请求走 ACP；显式模型和原生默认均能正确保存。
- 显式 CLI、显式 ACP、用户自定义 contract wrapper 和旧任务恢复保持原行为；显式选中的协议失败时不静默切换。
- 以真实组件提交或共享生产解析函数加 store/runner 集成测试覆盖，不在测试中复制一份 `launcherFor()` 算法来代替实际链路。

主要位置：[App.tsx](../../src/renderer/App.tsx)、[共享 Agent 定义](../../src/shared/agents.ts)、[defaults.ts](../../src/shared/defaults.ts)、[Agent 服务](../../src/main/buddy/agents/service.ts)、[核心服务](../../src/main/buddy/service.ts)、[Composer](../../src/renderer/components/Composer.tsx)。

### R2 [P1] 让 ACP 失败状态可恢复，并提供界面重试入口

**当前问题**

扫描按 Agent ID 继承所有历史 `failed`，成功握手又拒绝清除该状态。暂时启动失败、超时和登录失败被混在一起；修复后重新扫描仍不可用。完整 `probeLocalAgent()` 可以恢复，但设置页没有调用入口，失败行的模型控件又被禁用，用户无法通过正常操作触发恢复。

**稳定复现**

1. 假 ACP 第一次 initialize 返回错误，扫描记为 failed。
2. 修复同一个进程，使 initialize/session/new 都能成功。
3. 重新扫描：当前仍 failed，不能选择新任务。
4. 直接调用完整 probe：可变为 verified，证明程序本身已经恢复。

**修改要求**

- 分开“安装存在”“协议握手结果”“登录/会话结果”，至少记录失败发生在哪一层及结果对应的安装/启动配置。
- 暂时的 spawn、initialize、超时失败，在同一目标的新握手成功后可清除对应失败；不能把所有 failed 当成永久认证失败。
- 已知 session/new 认证失败不能仅凭 initialize 成功就标为登录恢复。
- 在失败或待验证的 Agent 行提供“重新验证”操作，调用受限的完整 probe；即使该行不能用于任务，也必须可以重试。使用逐行 busy、错误提示和库存事件更新，不锁住整页。
- 登录后用户可以点击重新验证恢复可用性，无需改动启动参数、清缓存或重启应用；全量扫描仍默认只做轻量探测。
- 结果绑定安装身份及启动配置指纹。切换路径、argv/env 或升级后不能直接继承旧目标的失败；并发旧 probe 不得覆盖新配置结果。
- 旧缓存的 failed 缺少阶段信息时，按“需要重新验证”迁移并提供恢复路径，不能未经验证就改为成功。
- 明确 handshake 通过与会话已验证的区别。没有会话证据时可以按产品策略允许进入启动前验证，但不能把它描述为已经登录；已知认证失败应提示修复。
- 更新后校验按安装与协议运行能力判断，不因历史登录错误永久阻止软件更新成功的判定，也不能跳过版本及目标归属验证。

**验收**

- 上述暂时握手失败用例在修复后重扫可恢复；原生认证失败用例在浅握手后仍提示登录，重新登录并点击完整验证后恢复。
- 设置页从失败到恢复的真实交互、库存持久化、重新打开页面和应用重启均覆盖。
- 旧失败探测与新配置保存并发时，旧结果被丢弃或仅作用于旧目标。
- 对现有 Claude/Codex/WeCode 使用假 adapter 做回归，不依赖修改用户真实账号。

主要位置：[Agent 服务](../../src/main/buddy/agents/service.ts)、[共享状态](../../src/shared/agents.ts)、[schema](../../src/main/buddy/schemas.ts)、[Agent 页面](../../src/renderer/components/settings/AgentsSettings.tsx)、[库存订阅](../../src/renderer/hooks/useAgentUpdates.ts)。

### R3 [P2] 清除模型缓存中的明文启动凭据

**当前问题**

CLI/ACP cache key 包含完整 command、args、env，原先仅用于内存，现在直接成为磁盘 `entries` 的键。API key 等字段因此被复制到 `agent-model-cache.json`，更换或删除配置后旧记录仍可能保留。

**稳定复现**

在临时 launcher.env 中设置一个模拟 API key，查询一次模型并读取缓存文件，当前可直接搜索到该模拟值。只使用模拟字符串，不读取或打印用户真实凭据。

**修改要求**

- 使用规范化启动上下文的不可逆摘要作为磁盘 key，例如 SHA-256；将协议、Actor、实际命令、argv、排序后的 env、必要的 cwd/隔离上下文纳入指纹。
- 凭据变化必须使指纹变化；不能仅将所有敏感值替换为同一个 `[REDACTED]`，否则不同账号会错误共享模型目录。
- 磁盘只保留摘要和模型目录所需字段，不保存用于计算摘要的原始启动上下文；command/args 也可能携带凭据。
- 增加缓存 schema 版本。启动初始化或首次加载旧缓存时，废弃或重写旧格式；即使此后没有新模型查询，也不能一直保留旧明文文件。
- 这是可重建缓存，不为旧明文内容创建备份，不把它写进日志、错误消息或迁移报告；不得删除原生账号配置或全局 launcher 设置。
- 原子替换、并发加载/写入去重继续有效；新写入应使用仅当前用户可读写的权限，且不能由排队中的旧格式写入重新覆盖迁移结果。

**验收**

- CLI 和 ACP 两条真实服务路径的缓存文件均不包含模拟 env、参数中的秘密值。
- 模型缓存命中、重启恢复、并发写入仍正常；两个不同凭据生成不同 key，env 对象键顺序变化不会无故产生新 key。
- 构造含模拟秘密的旧格式缓存，初始化迁移后文件内容不再含该值；重复迁移幂等，其他用户配置不变。
- schema 校验失败、空目录和不可读缓存均能降级；不回显缓存原文。

主要位置：[核心服务](../../src/main/buddy/service.ts)、[模型磁盘缓存](../../src/main/buddy/model-cache.ts)、[schema](../../src/main/buddy/schemas.ts)。

### R4 [P2] 在接受命令别名前验证产品身份

**当前问题**

`cbc` 被加入 CodeBuddy aliases，但发现阶段只依据可执行文件名和版本命令；launcher 又按 basename 识别为原生 CodeBuddy。任意同名程序都可能成为可用 Agent，甚至被关联到错误的更新目标。

**稳定复现**

临时目录只提供一个无 CodeBuddy 包归属的 `cbc`：版本命令成功，ACP 不支持。当前结果仍为 `runnable=true`、默认 CLI，并进入新建任务列表。

**修改要求**

- 为通用名称 alias 增加明确身份条件，先验证实际目标、可信包元数据或已知安装布局；必要时使用有界、只读的产品帮助签名。
- CodeBuddy 的 `cbc` 必须有可靠证据，例如目标归属于 `@tencent-ai/codebuddy-code`；任意版本号不是身份证明。
- 符号链接、版本管理器 shim 和原生安装可能采用不同证据，不能要求所有真实安装都必须是 npm 包。
- 身份未知或冲突时，不自动标为 runnable，不作为该产品进入任务选项，不生成该产品的更新目标；诊断信息可以解释未接受的候选。
- 同样审查本次扩充涉及的通用名称和别名。不要仅靠扩大 `commandKindFor()` 名单消除误判。
- 保留用户显式配置的合法自定义 contract wrapper，自动发现规则不能无理由覆盖或重命名它。

**验收**

- 真 CodeBuddy 包的 `cbc` 符号链接能发现；只有同名文件、无关包和伪版本输出不能冒充。
- 多安装中，一个身份不符的候选不能覆盖另一个已验证候选；不会对无关包提供 CodeBuddy 更新操作。
- 错误识别测试覆盖 runnable、任务选择及更新目标，不能只测 recipe 是否包含 alias。

主要位置：[产品规则](../../src/shared/agents.ts)、[候选目录](../../src/main/buddy/agents/discovery.ts)、[Agent 服务](../../src/main/buddy/agents/service.ts)、[launcher 分派](../../src/main/buddy/launchers.ts)。

## 4. B 部分：原方案补全与支持范围校准

### D1. 已知 App 内 CLI 与独立 adapter 发现

- 为确有公开或本机证据的产品添加已知 bundle 身份和相对 CLI 路径规则；不递归猜测整个 Applications 目录中的任意可执行文件。
- App 版本与 CLI 版本分开；仅存在 App 不代表可运行。App 内 CLI 作为现有产品的候选，不新增重复 Actor。
- 主 CLI 与本地 ACP adapter 分别采集，修复在查 adapter 之前就因主命令缺失而提前返回的路径。
- adapter 依赖未满足时明确显示缺少什么；存在 adapter 本身不能证明后端可用，不自动下载依赖。
- 验收使用临时应用包、失效内部入口、纯 App 和独立 adapter 夹具；规则依据和未支持布局写入能力记录。

### D2. wrapper、版本管理器和运行时一致性

- 有界解析已知管理器的 shim/wrapper，保留启动入口、真实目标、runtime 及安装来源；未知脚本不通过任意执行来猜测身份。
- 发现、版本查询、ACP 探测、真正任务和更新验证必须使用兼容的运行时环境。尤其 off-PATH 的 Node 安装，不能版本查询用一个 Node、任务启动又用另一个 Node。
- 多安装优先用户显式选择和 shell 当前入口，其他版本作为候选；不得因数值版本更高自动替换现有选择。
- 未知更新渠道继续只读，不因为解出包名就强制改用另一包管理器更新。
- 覆盖至少一个已知 shim、两个 Node 安装、包含空格的路径、断链和 wrapper 子命令场景。

### D3. 手动刷新更新路径快照

- “重新扫描/全部刷新”受限地重新读取用户 shell 的 PATH，使 Buddy 启动后新增的安装路径可以被发现；“仅检查更新”不必重读 shell。
- shell 超时或无效输出时保留原快照与既有库存，显示诊断并允许重试，不清空列表、不阻塞页面。
- 优先采用本次扫描和子进程的环境快照；若复用全局 PATH 更新，应保证正在运行任务的环境不受改变。
- 不把所有 Node 版本追加到全局 PATH。有关原生配置目录变量只按白名单处理，且服从已有隔离与显式 env。
- 缓存包含目录规则版本及必要的安装/环境指纹，升级规则后不能长期沿用过时判断。

### D4. 校准每个新增产品的支持级别

为 Gemini、Qwen、Copilot、Goose、Droid，以及已加入代码的 P2/P3 产品建立一张能力表，逐项记录：发现规则、身份依据、CLI 适配、ACP 实际入口、版本条件、模型与更新能力、自动化验证、真实环境验证。

- 首批四个新增产品及 Gemini 的 ACP 路线必须贯通任务创建、执行和恢复；仅有 recipe 或握手不能算完成接入。
- 对第二、三批，不能因命令看起来相似就声明原生 ACP；实施时核对官方来源及实际帮助，记录来源/版本/日期。没有依据的候选降为待验证或仅发现，并说明限制。
- 仅发现而未适配的产品不进入可执行任务选项，页面说明“执行方式尚未适配”，不要暗示安装失败。
- Gemini 原生 CLI 未实现时明确保留为待完成项，不能把拒绝 contract 回退算成实现了 CLI。
- 本机没有新增 Agent 时，列表不应凭空增加条目；不为了凑齐实测结果安装或升级用户的软件。
- 没有真实安装/账号时完成隔离集成验证并记录“真实生成未验证”；不得把假 ACP 服务结果写成该厂商真实验证通过。

### D5. 模型缓存与发现交互回归

模型缓存属于当前工作区已增加的范围，应在保留功能的前提下完成以下验证；其中后台刷新通知是本任务的验收要求，不属于前次四个已复现缺陷的重复声明。

- 旧模型列表可以先展示；后台刷新成功后，当前打开的设置、新建任务或 Composer 能收到新目录，不依赖用户切换 Actor 或等待下一轮长 TTL。
- 刷新失败时保留可用旧列表并提供可理解的错误/重试反馈，不默默吞掉所有失败；空目录与失败目录区分。
- 切换安装、协议、账号或任务上下文时，不显示其他上下文的模型；晚到结果不覆盖当前选择。
- 新的配置、默认模型和任务启用保存继续只影响对应目标，不触发整页等待或无关 Agent 的全量探测。

## 5. 实施顺序与测试要求

建议顺序：R1 → R2 → R3 → R4 → D1–D3 → D4–D5 → 回归验收。可以调整内部文件拆分，但不以目录重构代替行为修复。

将 review 的四项复现改成仓库内持久回归测试，先确认当前代码能暴露问题，再修复。测试应走生产逻辑，避免只断言新增 recipe 数量或复制实现算法。

| 验收组 | 必须覆盖的路径 |
| --- | --- |
| 新 Agent 默认协议 | 全新数据 → 发现 → 界面选中 → 模型查询 → 提交 → 读取任务配置 → runner 使用 ACP |
| 现有 Agent 兼容 | 原 CLI/ACP、自定义 wrapper、显式安装、原生默认/指定模型、旧任务会话恢复 |
| 失败恢复 | 暂时握手失败、认证失败、登录后重新验证、重启缓存、并发旧探测结果 |
| 缓存凭据 | CLI/ACP、env/args、旧 schema 迁移、凭据轮换、并发写入、原子替换 |
| 身份和安装 | 真/假 cbc、多安装、断链、App 内 CLI、独立 adapter、已知 shim、未知脚本 |
| 路径变化 | Finder 精简 PATH、运行期间 shell PATH 改变、shell 超时、off-PATH runtime |
| 任务执行 | 至少两个不同新 ID 的真实临时 stdio 两轮、恢复、dual-break、取消、超时、错误输出和模型传递 |
| UI 和缓存刷新 | 失败行重试、未安装不展示、发现但未适配不可选、后台目录更新、单行保存、窄窗口和明暗主题 |

先执行新增及受影响测试，再执行：

```bash
pnpm typecheck
pnpm test
pnpm build
pnpm test:e2e
```

- E2E 必须覆盖本任务修改的 Agent 页和新建任务链路，使用隔离 Buddy 数据与受控 Agent；不让测试刷新、更新用户真实安装。
- 全量测试失败时给出具体测试、错误及与未修改基线的比较；不凭历史记录将新失败归为既有问题，也不为本任务顺手修改无关模块。
- 本机只读证据与临时夹具结果分别记录。任何真实生成测试都应明确实际 Agent/版本、临时仓库、模型与结果，缺条件时列出未验证项。
- 修改模型缓存测试时保留错误反馈断言，不仅验证“列表还在”；修改 ACP 测试时同时验证失败保留和恢复，避免只测保留 failed。
