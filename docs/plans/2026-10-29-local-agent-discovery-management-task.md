## 1. 目标与范围

把 Buddy 的 Agent 配置从固定的启动器列表改为本机自动发现、按实际能力管理的 Agent 页面。用户打开设置后，就能看到本机已有的 Agent、实际安装版本、CLI/ACP 可用情况、默认模型、启动命令及更新入口；新建任务继续记住上次选择，只在没有记忆时采用设置默认值。

明确的产品要求：

1. 设置菜单新增 **Agent**，顺序为 **常规 → Agent → 外观 → 快捷键 → 提示词**，其余入口保持原位置。
2. 自动扫描本机安装情况，自动填入对应的启动命令和参数，允许用户修改并恢复自动值。
3. 探测实际 ACP 支持情况，区分原生 ACP、通过本机适配器提供 ACP、未安装适配器、不兼容、待验证。
4. 保留 CLI 和 ACP 两种执行方式，按每个 Agent 的实际能力提供选择。
5. **CLI 和 ACP 都纳入模型选择**：可枚举时下拉选择；只能指定模型时允许手动输入模型 ID；不能指定时使用 Agent 自身配置并说明原因。
6. 每个 Agent 可设置默认执行方式及默认模型。新建任务的角色和模型记忆优先，不被设置默认值覆盖。
7. 检测新版本，支持单个更新和全部更新，更新后验证实际安装及运行状态。
8. 参考用户提供的 Magpie Agent 列表截图及本地源码中的发现、版本展示和更新交互。

本次不包含：

- 网关、请求代理、模型供应商管理、流量路由、账号接管或改写 Agent 的服务端地址。
- 自动安装尚未安装的 Agent、Agent 安装市场、远程机器扫描。
- MCP、Plugin、Skill、Subagent 资源库管理；不把 v2.0.7 的资源库功能并入本次工作。
- 自动更新 Buddy 自身的改造；Agent 更新和 `src/main/updater.ts` 的应用更新保持独立。
- 发布新版本、制作安装包、替换已安装的 Buddy.app。

本阶段面向 macOS。未知 Agent 没有统一的本机发现或 CLI 约定，因此“自动扫描”指基于可扩展识别规则自动找到真实安装、解析启动方式并验证能力，不能承诺对任意可执行文件无条件识别并调用。

## 4. 设置页与交互

### 4.1 页面结构

```text
设置
  常规
  Agent  ← 新增
  外观
  快捷键
  提示词

Agent                              [重新扫描] [检查更新]
发现 N 个 Agent · M 项可更新                    [全部更新]

名称 / CLI 与 App 版本 / 高级 / 更新   当前方式   默认模型   任务启用
安装状态、可执行状态、必要的异常说明

行内展开高级：安装位置（多安装可选）、启动命令、参数、环境变量
参数/环境变量：JSON 着色、格式化、校验；超时使用常规统一设置
```

- 默认展示已发现产品及用户显式配置项。仅有残留配置的项目放在“不可用/待处理”区域，不能混入可运行清单。
- 有多个安装来源时，在同一产品的管理面板展示候选安装位置、版本、来源和当前使用项。
- CLI 与 App 的版本分开展示。更新 CLI 后不能把 App 版本也显示为已更新。
- 模型选择器随当前协议变化；不支持的协议禁用并说明原因，支持情况未知时提供检测入口。
- 单个更新放在版本旁；全部更新入口显示符合条件的数量与逐项结果，操作期间列表不跳动。
- 详细路径、启动诊断和更新日志放入管理面板，列表主行保持简洁。
- 原常规页的启动器配置移到 Agent 页。倒计时、失败阈值等协作策略保留在常规页。
- 如提供“在 Buddy 中使用”开关：关闭仅影响新任务选项，不卸载 Agent、不清除记忆、不更改现有任务。
- 所有文案使用 `useI18n`，覆盖 zh-CN/zh-TW/en；图标使用 lucide-react，兼容全部现有主题及键盘操作。

### 4.2 首次默认方式

已有用户选择优先保留。对于新发现且尚无配置的 Agent：CLI 已可运行时默认 CLI；仅 ACP 可运行时默认 ACP；两者均未验证时不自动标为可执行。检测到新增 ACP 支持不会悄悄把已有 CLI 配置切换为 ACP。

## 5. 自动发现与目标身份

### 5.1 发现来源与触发时机

发现来源包括：当前有效 PATH、带超时的登录 shell 环境、常见用户安装目录、已安装包的元数据、`/Applications` 与 `~/Applications` 中已识别的应用，以及用户已保存的自定义启动器。复用现有 shell 处理，保留用户显式环境变量优先级。

Node/Python 等版本管理器下的安装，必须跟踪其实际解释器、包管理器和安装前缀；不能只在当前 PATH 中找到一个同名 npm 就拿来管理所有安装。

触发规则：

- Buddy 启动后异步发现；首次进入 Agent 页自动刷新过期结果。
- “重新扫描”清理路径/安装/能力的相关缓存，再扫描；安装或卸载后的结果可立即更新。
- 更新成功、修改启动配置、切换安装位置后，定向重新探测受影响项目。
- 新建任务使用共享发现结果，不再另维护静态名单；发现进行中显示状态，不阻塞整个窗口。

扫描不遍历整块磁盘，不遍历用户所有聊天历史；不执行任意未知二进制的猜测参数。只对已识别目标执行受控版本/能力查询，未知自定义命令保留为待验证，用户主动测试后才能认定可用。

### 5.2 状态必须分开

| 维度 | 必须表达的状态 |
| --- | --- |
| 安装 | 已安装、仅配置残留、缺失、读取失败 |
| 运行 | 可执行、缺解释器/依赖、需要认证、待验证、不可运行 |
| 协议 | CLI 可用；ACP 原生/适配器可用；适配器缺失；协议不兼容；未知 |
| 模型 | 已获得列表、只知道当前模型、允许手动 ID、使用原生默认、查询失败 |
| 更新 | 检查中、可更新、当前渠道最新、离线/失败、来源未知、需要外部更新 |

单个项目失败不得中断其他项目。扫描失败或目录无权限时保留上次结果并标明过期，不能据此删除用户配置或报告“已卸载”。目录中只有 Skills、日志或缓存不构成可执行安装证据。

### 5.3 三层身份

| 对象 | 责任与稳定性 |
| --- | --- |
| `AgentDefinition` | 产品/逻辑 Actor 的识别规则、显示名、运行适配、模型查询和更新规则；旧 Actor ID 保留 |
| `AgentInstallation` | 一个实际安装实例：安装渠道、稳定安装位置/前缀、入口路径、realpath、版本、包身份及所属应用 |
| `ResolvedAgentTarget` | Buddy 实际调用的目标：安装实例、CLI/ACP、wrapper/adapter、底层 Agent、argv、环境、有效 home/config、cwd |

安装 ID 不得依赖版本号或版本化 Cellar 路径；同一安装升级后身份稳定。不同安装前缀分别管理。入口符号链接与 realpath 都需记录，以便版本目录变化后仍能找到同一安装。

自动选择顺序：用户指定安装/命令 → 已保存且仍有效的安装 → 有效 PATH 中的优先项 → 已验证的其他安装位置。用户指定项失效时标为失效，不能偷偷换成另一份安装。

WeCode 的多个 Actor 共享安装包，但具有不同子命令及配置上下文；子命令分别探测，包只更新一次。ACP 适配器与底层 Agent 分别记录版本和安装身份。Codex App 内置 CLI 与独立 CLI 不得混为一份安装。

### 5.4 首批覆盖要求

- 覆盖现有 10 个 Actor 的发现、启动配置迁移和原有运行路径。
- 覆盖截图中的其他产品安装识别：Claude Desktop、Zed、VS Code、WorkBuddy、CodeBuddy，以及 Codex/DeepSeek Harness 的桌面应用版本。
- 桌面应用“已安装”不等于它是可供 Buddy 调用的 ACP 服务端。只有验证到可驱动的 CLI/ACP 端点才进入任务角色选项；否则仍可展示安装和版本，更新按其真实渠道提供能力或外部入口。
- 首批至少用一个原名单外的真实 CLI 产品验证完整发现到运行链路，优先调查截图中的 CodeBuddy CLI；实际协议/模型能力在实施时按该安装版本验证，不提前承诺。
- 另用一个不在任何旧枚举中的通用 ACP 测试 Agent 验证：新增注册信息后，无需修改任务 UI、状态机或消息角色枚举，即可完整执行两轮任务。
- 保留自定义本机 Agent 入口，用户可指定命令、协议和参数。未识别 CLI 必须有运行适配或显式 Buddy contract 声明；不能给任意 CLI 自动追加 Buddy contract 参数。

## 6. CLI/ACP 能力探测

### 6.1 探测层次

1. **安装识别**：文件、应用元数据、包管理器记录、真实入口位置。
2. **轻量运行探测**：已知 recipe 的版本/帮助信息；支持的 CLI 输出格式和非交互调用方式。
3. **ACP 握手**：以真实配置启动 stdio 端点，执行 `initialize`，检查协议版本及返回能力。
4. **会话/模型查询**：需要时调用会话建立和模型查询路径，验证是否需要登录、是否能创建会话；不发送生成 prompt。
5. **显式运行测试**：沿用启动器测试/任务健康检查能力，验证真实输出与任务协议，独立于后台扫描。

ACP 支持必须记录握手证据、时间、目标版本以及原生/适配器来源。帮助文本、文件名含 `acp` 或存在适配器文件都只能构成候选依据。握手通过但会话需登录，应显示“支持 ACP，需要登录”，不能变成“不支持 ACP”。

当前 Buddy 客户端使用 ACP v1。探测应验证实际协商版本；遇到不支持的版本关闭连接并报告不兼容。本次不顺带实现 ACP v2；官方页面当前也将 v2 标为 Draft。依据：[ACP v1 初始化与版本协商](https://agentclientprotocol.com/protocol/v1/initialization)。

### 6.2 探测约束

- 自动探测不安装 adapter，不运行会下载包的 `npx -y`，不自动登录，不发起生成请求，不修改原生 provider/base URL。
- 缺少本地适配器显示“需要安装适配器”，提供可查看的安装说明；安装新依赖不属于自动扫描。原有显式配置的 npx launcher 保留，但不能在扫描中隐式执行下载。
- 不能通过默认给所有命令追加 `acp` 探测能力；各 recipe 明确候选入口，用户自定义入口单独验证。
- 自动探测使用受限客户端能力，不接受探测过程中要求的文件写入、终端执行或权限提升。
- `session/new` 可能由 Agent 写入会话元数据，不能声称严格零副作用；限制探测频率，避免在用户项目发送 prompt 或创建任务文件。主列表扫描不强制为所有 Agent 建会话。
- 单项目有总超时与进程树清理；默认版本查询 3 秒、握手 10 秒、含模型查询的完整探测不超过 30 秒。并发上限默认 4，提供取消并拒绝旧请求覆盖新结果。
- 模型和能力缓存至少纳入安装/二进制版本、协议、adapter、argv、相关环境指纹、有效配置根及 cwd。凭据不得明文写入缓存 key 或日志。
- 正式执行、模型探测、测试启动器、健康检查、提交信息生成共用目标解析，不能分别猜测 Agent 的 home 或底层 CLI。
- 保持 `docs/acp-codex-storage.md` 描述的 Codex/WeCode ACP 隔离与认证边界；不能为扫描简便直接切回公共 home。

## 7. 模型选择、默认值与任务记忆

### 7.1 CLI 模型选择是本次必做功能

CLI 没有统一模型接口。provider 必须分别声明以下能力，不能只用一个 `supportsModel` 布尔值：

| 能力 | 实现与 UI 行为 |
| --- | --- |
| 可枚举模型 | 调用目标原生查询接口或可靠本地目录，展示真实 ID、显示名和来源；按需刷新 |
| 可指定模型但无法枚举 | 提供手动 ID、已验证的历史选择，以及“使用 Agent 自身默认” |
| 只能读取当前值 | 显示当前模型；不把单个当前值伪装成完整可选列表 |
| 不支持外部指定 | 显示“使用 Agent 自身配置”，模型选择控件说明限制 |
| 续聊可否切换模型 | 独立声明并验证；不支持时禁止在既有会话中假装切换成功 |

CLI 的模型值通过该 CLI 已验证的参数、环境变量或原生会话接口传入。不同 CLI 分别适配，不能一律添加 `--model`。不修改用户的原生全局配置文件，也不引入统一供应商/模型路由层。

实施时为每个首批 CLI 记录：版本、模型查询方式、模型选择方式、参数位置、是否支持 resume 时指定，以及真实验证结果。没有证据的能力标为未知或受限，不猜测模型名和参数。

手动命令已包含模型参数时，解析器需识别并展示实际值。任务选择覆盖默认模型时，必须按该 CLI 规则替换已识别的模型参数，避免重复参数；如果自定义 wrapper 或高优先级环境导致无法可靠覆盖，提示冲突，不能界面显示 A、实际运行 B。

### 7.2 ACP 模型选择

复用并完善 `acp/models.ts`：兼容现有 Agent 返回的 `models.availableModels`，并处理会话 `configOptions` 中的模型选项、分组选择及当前值；设置时使用目标实际支持的接口。不能把固定的云端模型名单套到所有 Agent。

`configOptions` 的选项 ID、值及顺序由 Agent 返回；保存真实值，展示名称只用于 UI。依据：[ACP v1 Session Config Options](https://agentclientprotocol.com/protocol/v1/session-config-options)。

CLI 与 ACP 的模型 ID、可用列表可能不同，分别缓存和保存默认值；只有确证映射关系时才能跨协议转换。

### 7.3 选择优先级

**模型：本次弹窗明确选择 → 当前角色及 Agent/协议的上次记忆 → Agent 页该协议的默认模型 → Agent 自身默认。**

“使用 Agent 自身默认”是一个明确选项，也可以被记住；它与“没有保存过选择”不同。记住该选项时不能再用设置页默认模型覆盖。

协议在 Agent 页设置为该 Agent 的默认执行方式；新建任务继续沿用现有方式，不强制增加协议控件。当前 v2.0.6 没有单独的任务创建协议记忆，不能虚构旧记忆；历史任务仍使用自身保存的协议。未来若增加弹窗协议选择，遵循本次明确选择/记忆优先。

角色选择延续上次 implementer/reviewer 记忆。首次无记忆时，已安装且可运行的 Claude/Codex 仍可作为原有默认；缺少其中之一时从动态可用项提供明确选择，不静默选用未安装项。同一逻辑 Actor 不得同时担任两个角色，保持现有约束；不足两个可用项时给出可操作提示。

### 7.4 记忆与失效处理

- 角色继续使用全应用范围的上次记忆；模型记忆按角色、稳定 Agent ID、协议和有效配置上下文区分，避免把另一 Agent 的同名模型误用过来。
- 迁移现有四个 localStorage key；旧模型只能绑定到其对应的旧角色、Agent 和已保存协议。旧空字符串视为无模型记忆，不改变用户原有选择。
- 用户切换 Agent 后读取该目标的记忆/默认值，异步返回的前一个 Agent 模型列表不能覆盖当前选择。
- 打开/取消弹窗、后台扫描及修改设置默认值不更新任务选择记忆；创建操作沿用现有记忆交互。
- 已明确被完整模型列表判定移除的记忆保留并标为失效，提示用户选择，不能无提示换成第一个模型。
- 仅因离线、认证或查询失败，不能判定模型已被移除，更不能清空记忆。允许使用此前有效或手动指定的模型，实际执行前完成可行性检查。
- Agent 已卸载或用户禁用时保留角色记忆并提示重新选择，不悄悄换成另一个 Agent。
- 设置页默认值变更只自动影响没有记忆的新选择；失效记忆的替换由用户明确选择。运行中、排队中及历史任务的快照不随全局默认变化。

### 7.5 任务运行快照

创建任务时保存选中 Agent 的有效安装引用、协议、命令/参数、必要环境、模型选择方式及值。主进程使用同一解析逻辑复核 Renderer 的选择，避免只有 UI 应用了默认值。

“使用 Agent 自身默认”以明确策略保存，不凭空填入模型名；若 Agent 自身配置变化导致实际模型变化，运行记录展示实际结果。指定模型时必须真实传递，并在 Agent 提供回报时记录实际模型。

稳定入口引用允许同一安装升级后的路径变化；不能重新选择到另一个安装来源。原入口缺失时标明错误并允许修复，不改写历史快照来掩盖失效。

Composer、启动前健康检查、会话恢复及提交信息生成使用任务快照。模型在恢复路径上不支持切换时给出明确限制，不能默默丢弃模型值或丢失会话。

## 8. 新版本检测与更新管理

### 8.1 检查更新

- 当前版本来自实际安装元数据和受控版本命令，保存原始版本文本；无法解析时显示未知，不进行字符串大小比较。
- 最新版本取自当前安装所属渠道。区分 Homebrew formula/cask、npm/pnpm/bun、uv/pipx、官方自更新或应用自身渠道；仅对已实现并验证的渠道启用更新。
- 首批渠道适配必须覆盖 Homebrew、npm/pnpm/bun，以及首批 Agent 实际采用且具有稳定接口的官方自更新、uv/pipx。逐项记录支持矩阵和限制；不能把已明确识别的常见安装一律标为“来源未知”来绕过更新需求。桌面应用没有可自动执行的更新接口时提供其原生更新入口，并明确不计入可批量自动更新数量。
- 检测器输出包管理器绝对路径、安装 prefix、包名、渠道及证据。不能用 npm 去覆盖 Homebrew 管理的同名程序，也不能把 App 内置 CLI 当全局 npm 包更新。
- 沿用原 stable/prerelease 渠道，不自动降级，不在包源不同的情况下比较版本。日期/hash 等非 SemVer 使用该产品规则；无法可靠比较就标为未知。
- 打开 Agent 页异步检查过期结果，默认成功缓存 6 小时、失败短暂退避；“检查更新”可强制刷新。断网/限流显示失败和上次检查时间，不能显示“已经最新”。
- 检查更新只读；没有用户点击更新时，不下载或安装版本。

### 8.2 单个更新与全部更新

两种入口使用同一个主进程更新服务。页面展示实际目标和来源，用户点击后即可执行已确定的更新方案，不额外增加每一步确认。

- 单个更新针对选中的安装实例。全部更新只包含当前列出的、确有新版且能由 Buddy 管理的安装；不顺便升级其他未选中的同名安装或本机全部软件。
- 全部更新串行执行；单个入口也进入同一队列，防止共享包管理器/prefix 并发写入。重复点击不得重复启动。
- WeCode 等共享包、多个角色共用的 adapter 按安装包去重，显示所有受影响 Agent。
- 更新任务状态至少包括：排队、检查条件、更新中、验证中、成功、失败、跳过、已取消/已中断。
- 单项失败后继续其余项，汇总每项的更新前后版本与错误；允许重试失败项。
- 取消批量更新默认停止尚未开始的项目，当前包管理器事务完成后再停止；不要因关闭面板而中途杀死安装事务。
- 应用重启后读取持久作业状态；未完成项目标为中断并重新检测，不能沿用“成功”状态。

### 8.3 与运行任务互斥

更新锁按实际安装包及依赖建立。Agent、底层运行时、adapter 或共用 wrapper 正被 Buddy 执行/探测使用时，不直接替换它们。

- 点击更新时若正在使用，显示“使用中，暂未更新”，批量操作继续其他项目；不自动终止任务。
- 开始更新与启动新一轮/健康检查必须原子互斥，不能先检查为空闲、随后同时启动。
- 队列中尚未运行的任务可继续保留；轮到该安装时明确等待更新完成，不能把更新锁当成 Agent 故障并触发失败累计或 dual-break。
- 更新完成后再释放锁；必要的健康检查失败应报告具体原因，不影响其他 Agent 任务。
- 桌面应用更新需要关闭应用、管理员权限或原生更新界面时，显示具体限制/外部入口，不假装可以后台完成，也不擅自关闭用户应用。

### 8.4 更新完成的判定

成功必须同时满足：更新命令成功退出、目标安装重新识别成功、版本结果符合当前渠道的目标、实际入口可以运行版本检查。不能只看包管理器输出或 package.json 版本。

更新后清理该安装的发现、能力和模型缓存，重新验证当前使用协议。安装成功但 ACP/模型探测失败时分别显示“版本已更新”和“能力待修复/待验证”，不能合并成“全部正常”。

来源不明、无权限、程序升级后损坏时保留错误及可执行的修复说明。更新操作只执行已识别渠道的程序与 argv；Renderer 不传任意 shell 更新脚本。输出通过 `redact.ts` 脱敏。

第三方更新并不普遍支持自动回滚；本次不承诺自动回退所有 Agent 包。保留前后版本和原渠道信息，按该渠道能力提供恢复方式，不自动改装到另一安装渠道。

## 9. 启动配置与持久化设计

### 9.1 自动值与用户覆盖分离

每个 Agent 的 CLI/ACP 分别保存自动发现配置和用户覆盖。最终值为“用户覆盖字段优先，未覆盖字段取当前发现值”。

- `command` 保存可执行入口，`args` 保存字符串数组；兼容旧 command 内含参数的格式，迁移时用已有 tokenizer 并补齐引号/空格测试。
- 参数编辑不能使用简单空白切分；必须可往返保存带空格路径、引号、空参数及子命令。
- 用户指定空参数数组也算覆盖，不能被“缺少参数时追加 acp”的逻辑覆盖。
- 切换 CLI/ACP 保留两套配置，不因切换删除另一套命令、参数和默认模型。
- 重新扫描和更新只刷新自动值，不覆盖手工值；提供按字段及按协议“恢复自动配置”。
- 可展示解析后的完整启动方式，但敏感环境变量默认脱敏。自定义 wrapper 不可解析时明确展示限制。
- 不扩大现有权限绕过参数的适用范围；新 Agent 的权限行为由自身已验证适配决定。

### 9.2 推荐存储边界

| 数据 | 推荐位置与要求 |
| --- | --- |
| 启用状态、选中安装、协议默认、各协议模型默认与覆盖 | 全局 settings 的独立 `agent_management` 区段，包含 schemaVersion |
| 发现与版本/能力缓存 | `dataRoot/global/agent-inventory-cache.json`，可失效重建，不替代用户配置 |
| 更新作业及结果 | `dataRoot/global/agent-update-jobs.json` 及脱敏日志，跨窗口统一 |
| 任务有效启动配置 | 任务 `settings.json`，保留旧 `launchers` 兼容映射 |
| 新建任务记忆 | 现有 localStorage 迁移为有版本的结构，保留旧 key 的迁移依据 |

设置变更由主进程按 Agent/字段合并，避免两个窗口把过期的整份 GlobalSettings 相互覆盖。更新 `normalizeGlobalSettings` 与 Zod 读取 schema，确保新字段不会被归一化丢弃。遵循仓库约定：JSON 使用 `.tmp → rename` 原子写，读取时做 schema 校验；未知 Actor 数据不丢弃。

历史 launcher 优先作为用户配置迁入；不能因为命令恰好等于旧默认值，就推断用户从未手工配置并覆盖它。缺失安装的历史 launcher 保留为不可用记录。

## 10. 动态 Agent 必须贯穿执行链路

禁止只把设置页改成动态列表，而继续依赖固定 10 个 Actor 执行任务。

1. 注册表统一提供 Agent ID、显示名、能力及解析目标；Renderer 的 `Actor` 不再是封闭的 10 项枚举，未知产品有通用显示回退。
2. 旧 `RUNNING_CLAUDE` 等状态继续兼容读取；新增通用 `RUNNING_AGENT`，由 `active_run.actor` 表达新 Agent 身份。既有生命周期和 dual-break 规则保持不变。
3. 新 Actor 消息保留其真实 ID，不能在 `normalizeActorRole()` 中降为 `system`。同步调整 transcript 类型、显示、统计和事件处理。
4. 通用 `actor_sessions` 作为新 Agent 的会话来源；增加通用 seed 映射，旧 seed/session 字段继续兼容。会话重置不得清除另一 Actor 的会话。
5. CLI 适配声明命令构建、输出解析、resume、模型参数；ACP 走通用传输和能力检查。未知 CLI 不自动套用 Claude 参数或 Buddy contract 参数。
6. 新建任务、Composer、健康检查、恢复、压缩/重试、提交信息生成都从能力注册表和任务快照解析。缺失能力时明确降级或禁用相应操作，不能换 Agent 执行。
7. 队列、倒计时、中断、重启恢复及 dual-break 必须覆盖新 Agent，避免新增通用运行状态导致永久占用队列或读取 state.json 失败。

| AC-10 | CLI 模型下拉 | 可枚举 CLI 展示其真实模型，选择后实际启动参数/回报与选择一致，不改原生全局配置 |
| AC-11 | CLI 手动模型 | 无列表但可指定的 CLI 支持输入与历史选择；不可指定的 CLI 明确限制，不虚报生效 |
| AC-12 | 模型参数冲突 | 已有模型参数及环境覆盖被正确处理；无重复冲突参数；无法覆盖时给出明确错误 |
| AC-13 | ACP 模型 | 旧 models 与 configOptions（含分组）可用；实际发送模型 ID；模型查询失败区别于空列表 |
| AC-14 | 无记忆使用默认 | 清除选择记忆后新建任务采用 Agent 页默认模型；未配置默认时使用原生默认 |
| AC-15 | 记忆优先 | 记住模型 A 后把设置默认改 B，再新建仍选 A；明确记住原生默认时也不被 B 覆盖 |
| AC-16 | 记忆隔离与竞态 | Agent/协议切换不串模型；过时请求不覆盖新选择；旧 key 迁移保留用户选择 |
| AC-17 | 失效和离线 | 模型明确移除会提示；单纯查询失败不清除记忆；卸载/禁用 Agent 不静默替换角色 |
| AC-18 | 任务快照 | 修改全局默认不改变既有/排队任务；恢复会话使用原任务模型策略，续聊限制有说明 |
| AC-19 | 真实新 Agent | 至少一个旧名单外的真实 CLI 及通用 ACP 测试 Agent 完成两轮；不靠增加界面/状态机枚举实现 |
| AC-20 | 完整生命周期 | 新 Actor 的 state.json 可读取，消息非 system，暂停/中断/重启恢复/队列/dual-break 无回归 |
| AC-21 | 更新版本来源 | 不同渠道按各自版本检查；离线、预发布、未知版本不被错误显示为最新或需要降级 |
| AC-22 | 单个更新 | 只更新目标安装，保留其他版本及用户参数；确认新版本且实际入口可运行 |
| AC-23 | 全部更新 | 串行、去重、进度明确；一项失败不阻断其他项；共享 WeCode 包/adapter 只更新一次 |
| AC-24 | 更新与任务竞争 | 正在使用的安装跳过；更新和新一轮启动互斥；不杀任务、不错误累计失败或确认 break |
| AC-25 | 假成功与能力退化 | 安装 exit 0 但程序损坏不算成功；安装成功但 ACP 失败分别呈现 |
| AC-26 | 取消与重启 | 取消后未开始项目不执行；关闭页面不中止安装；重启后中断项目重新检测 |
| AC-27 | 旧任务兼容 | 原 10 个 Actor、自定义 launcher、seed/session、CLI/ACP 及历史消息可继续读取和使用 |
| AC-28 | 业务边界 | 无网关/地址改写/账号接管；不自动安装新 Agent；Buddy 自更新保持原行为 |
| AC-29 | UI 与数据质量 | 三语言、主题、键盘、窄窗口可用；敏感值脱敏；缓存和设置原子写、多窗口不丢覆盖 |

## 13. 验证、落地与回退

### 13.1 自动化验证

- discovery/probe 测试使用临时安装目录和可控子进程，覆盖真实 argv、超时、退出及清理，不扫描或更新测试机的真实软件。
- 更新测试用假的包管理器/元数据服务覆盖串行、共享包去重、版本未变化、缺依赖、来源错配、任务锁竞争、重启恢复。
- 动态 Actor 测试通过实际 runner→store→schema→恢复路径，不只验证命令构建器。
- Renderer 测试覆盖菜单顺序、协议/模型能力、记忆优先级、参数恢复及部分失败展示。
- 完成定向测试后执行 `pnpm typecheck`、`pnpm test`、`pnpm build`，再执行相关 E2E；失败需区分基线问题和本次引入。

### 13.2 本机真实验证

实施时生成 `docs/agents/capability-baseline.md`，每项记录 Agent/安装路径/版本/来源/协议/模型能力/验证时间。用实际本机结果与列表逐项对照，不能把 registry 数量当发现数量。

至少验证：一个既有原生 CLI 的模型指定、一个适配器 ACP、一个原生 ACP（如本机具备）、一个原名单外产品、一个多安装场景及一个失效入口。不可用环境写明未验证项，不能以模拟通过替代实测声明。

真实更新验证使用明确用于验收的安装环境/副本：验证单个和批量更新的前后版本、实际命令可运行及协议重探测。不得为了文档或普通单测升级用户工作机 Agent。

### 13.3 迁移与回退

- 迁移首次运行前保留旧全局设置与记忆的可恢复备份，记录迁移版本，重复执行幂等。
- 分阶段落地：存储与解析 → 发现/能力 → 执行兼容 → 页面与记忆 → 更新管理 → 验收；阶段顺序不改变完整交付范围。
- v2.0.6 不能理解新增通用运行状态或新 Actor 的全部数据。回退测试在数据副本中进行；正式回退应保留新任务数据并恢复兼容快照，不能声称所有新任务都可由旧版继续执行。
- 不重置旧任务的会话、认证目录或原生配置；不删除已发现但暂时离线/缺失的用户配置。
- 完工说明必须分别列出：实现范围、自动化验证、本机实际验证、更新验证和未覆盖限制。任务文档完成不代表功能已经实现。
